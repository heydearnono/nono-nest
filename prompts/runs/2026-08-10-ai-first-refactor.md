# 把 nono-nest 改造成 AI 先行项目

- 日期：2026-08-10
- 场景：项目结构改造 / 元工作（不是业务功能）
- 参与：Ducc（Opus 5）

## raw prompt

原样保留，含笔误：

```text
这个项目我希望是 AI 先行的一个项目，所以所有的代码都应该是 AI 文档现行，以及 prpmpt 的不断迭代，那么我这项目应该怎样改造
```

追问一轮后补充的关键约束：

```text
嗯 我觉得 文档比代码量大的情况是符合预期的，毕竟后续也是 AI 维护
```

## 这次 prompt 缺什么

raw prompt 说清了方向（文档先行 + prompt 迭代），但没有给出：

- **判据** —— 「AI 先行」达成没达成，用什么检验？没有这一条，输出必然是一堆 md 文件。
- **规模预期** —— 项目本体只有 1 个页面 + 1 个纯函数，文档铺多厚？
  这一条在追问后才补上（文档多于代码是预期结果），它直接改变了方案的取舍。
- **已有约定** —— 工作区里已有三种 AI 文档方言（`android-platform/AGENTS.md`、
  `check-loop/AI.md`、`github-node-playground/docs/superpowers/`），不说 AI 会发明第四种。

## improved prompt

下次提同类需求可以直接用这个形状：

```text
把 <仓库> 改造成 AI 先行项目：业务代码之前必须先有 AI 可读的设计文档，
prompt 的迭代过程本身入库。

判据（最重要）：文档与代码的一致性必须是可失败的断言，进 CI，不靠纪律。
说明你用什么机制实现这一点。

上下文：
- 仓库现状：<技术栈、已有工程化能力、业务代码量>
- 工作区已有的 AI 文档约定：<列出，要求复用而非新造>
- 项目定位：<规模、是否发布、维护者是谁>

约束：
- 文档量大于代码量是预期结果，不必为「显得轻量」而砍掉必要结构
- 不预建空目录、不写占位文档，结构按需长出
- 收尾跑 <门禁命令>，绿了才算完成

输出：先给判断和机制设计，确认后再落地文件。
```

改动最大的一处是**把判据提到最前面**。原始 prompt 里「文档先行」是个愿望，
加上「必须是可失败的断言」之后，它变成一个有验收标准的工程问题，
方案自然收敛到 Spec ID + `validate-docs.mjs`，而不是收敛到「多写几篇 md」。

## 实际结果

AI 先做了调研（读三个参照仓库 + 现有工程化配置），再给方案，确认后落地：

- `AGENTS.md` —— 抄 `android-platform` 的骨架（既定事实表 / 术语字典 / 行为规范），
  换成小程序约束，新增第 4 节 Spec ID 机制
- `docs/vision.md`、`docs/glossary.md`
- `docs/features/greeting/{doc.md,tasks.md,summary.md}` —— 反向补写，作为机制样板
- `scripts/validate-docs.mjs` —— 五项校验，挂进 `npm run check` 与 CI

直接可用。一处需要注意的自觉行为：AI 在 `greeting/summary.md` 里主动记下
「这个功能违反了文档先行，规格是反向整理的」，没有假装它走了正序。

## 复盘

- **下次应提前给的上下文**：工作区已有的约定清单。不给就会新造方言。
- **判据比方案值钱**：一句「必须可失败」比十句「要重视文档」有效。
  同类元工作 prompt 都该先写判据。
- **是否提成模板**：暂不。这类「改造仓库工作方式」的需求预计不会频繁出现，
  按 `prompts/README.md` 的约定，等第二次真实使用再提炼。
