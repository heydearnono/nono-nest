## 原始 prompt


## 这一轮的三个判断

**「下一步」不等于阶段表的下一行。** 阶段表写的是 P3 = `POINT` + `REWARD` + `ACHV`
三个区。逆向线上代码后发现勋章只有两个产出点（今日全勤、成就解锁），而今日全勤要
8 条核心 id 全打满，其中 4 条要 P5 / P6 的页面才可能被打上 —— 所以现在做 `REWARD`
等于做一个换不了东西的兑换页。把 P3 拆成 P3-a（`POINT`，现在做）与 P3-b（等 P5 / P6），
并把这个依赖写回 `vision.md`，而不是硬按表往下推。

**推翻了上一轮自己写下的设计建议。** `habit/summary.md` 里我建议 P3「页面层先 `check`
再发放」。实际写的时候改了主意：两步走意味着页面可以只做一步，
「每条 `checks` 项都有一条 `earn` 流水」这个不变式就没有任何东西保证它。
改成在 `point.js` 里合成 `checkAndAward` 一个函数，并**回头把那条建议改掉** ——
留着一条已经不成立的建议在仓库里，下一个读它的 AI 会照做。

**主动偏离线上，并把偏离的代价写清。** 线上按 `task.category` 查 `pointRules` 三档费率，
任务自身的 `starsReward` / `foodPointsReward` 是死字段（逆向确认：只有家长端新建任务时
写入，没有任何读取点）。本仓库反过来只读任务字段，收益是 `utils/save.js` 一行没改；
代价是家长端改产出值变成按任务改，且导入线上 JSON 时家长改过的费率会丢。
两条都写进了 `doc.md`，不留给将来的人自己发现。

## 这条 prompt 缺什么

同 P2：三个字能跑完一个阶段，靠的是仓库里已有的阶段表、宪法和门禁。
但这轮暴露了一个新问题 —— **prompt 没有说「遇到阶段依赖倒挂时该怎么办」**。
我的处理是自己拆段并写回 `vision.md`，这是个产品决定，理想情况下应该让人拍板。
改进版 prompt 里应该有一句：

> 如果下一阶段的前置条件还没就绪，先说明依赖关系并给出拆分方案，不要直接开工。

## 复盘

**流水与货币刻意对不上，这件事值得单独测。** 货币花光后取消打卡会少扣，但流水记应扣的量。
`POINT-10` 同时断言了两边，就是为了让后来的人不会把它「修」成一致 ——
这类「看起来像 bug 的正确行为」，光写注释挡不住，得有一条断言站在那里。

**「不做」的清单比「做了」的更花时间。** 这一轮范围外写了 6 条，每条都要先逆向确认
线上是怎么做的、再说清为什么现在不做。但这是 `doc.md` 里最有价值的部分：
下一个人打开它，第一个问题就是「勋章为什么是 0」。
