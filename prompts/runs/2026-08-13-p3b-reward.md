## 这一轮的三个判断

**逆向读出来的四个毛病里，三个是同一个病根：一份数据存了两份。** `rr` 与 `tasks`
各存一份核心名单（删任务后全勤永久不可达）、`medalProgress` 与判据各存一份进度
（解锁后进度条冻结）、周奖励与 `full-week` 各存一套「达标」口径（同一件事两个答案）。
本轮的做法不是逐个防住，而是让它们**表达不出来**：`core` 落在任务元素上，
进度每次现算不存，达标日只有 `isQualifiedDay` 一个函数且 `minDays` 是 import 来的。
第三条尤其是 P5 识字那一轮教训的复用 ——「共用判据要共用的是函数，不是调用另一个入口」。

**「不扣勋章」这个 bug 的正确修法是改流程，不是加校验。** 线上申请时不扣、批准时才扣，
中间勋章被花掉那条 pending 就永远批不了（`approveExchange` 里余额不够直接 return，
既不提示也不删记录）。能想到的修法有三种：批准时余额不够就自动驳回、申请时冻结勋章、
申请时直接扣。选第三种的理由不只是简单 —— 它让本轮**不需要写审批函数**，
而家长端要 P7 才有入口，写了就是不可达代码（第 5 节第 4 条）。
一个流程决定同时消掉了一个 bug 和一段死代码。

**结算挂在哪里决定了会不会漏。** 线上在四个打卡调用点各写一遍全勤与成就结算，
漏一处就是「这类打卡不发勋章」。本轮挂进 `checkAwardAndGrow` 一个函数 ——
四条打卡路径本来就全走它，所以一处挂上等于五个页面一起接上。`REWARD-13` 断言的是
「一次调用就发勋章」，作用是挡住下一个人把它拆成「页面先打卡、再调 settleDay」两步走。

## 这条 prompt 缺什么

**`ACHV-01` 的期望值是错的，而错法是「照直觉写全 0」。** 空存档十一条进度并非全 0：
`pet_level` 读 `pet.petLevel`，而宠物等级的初始值是 1。这条在写 `doc.md` 时没算，
在写测试时才红。改的是**规格**不是断言 —— 空存档显示 `1/5` 是对的，那只小伙伴确实存在；
把它按到 0 要给这一条单独减 1，那就是本轮一直在躲的「同一份数据两套口径」。

规律：**规格表里凡是「全 X」这种量词，得逐条代进去验一遍。** 上一轮的教训是
「规格之间要交叉验算」，这一轮是「规格里的全称判断要展开」——
`every` 型的期望值只要有一个反例就整条失效，而反例往往来自另一个域的默认值
（这里是 `SAVE` 区的 `petLevel: 1`）。

**页面 toast 该按什么判断，`doc.md` 只写了优先级、没写数据来源。** 第一版实现读
`rewardState().allDone`，逻辑上「今天发过全勤」为真就恭喜 —— 于是今天第二次进奖励中心
还会再恭喜一遍。改成比**结算前后两份存档的水位差**。这不违反「页面不做业务判断」：
比两个水位是适配层的事，判据仍然只在 `utils/` 里。已回填进 `doc.md`。

## 复盘

**测试失败两次，两次都在同一类：期望值从直觉来而不是从契约来。** 一次是 `ACHV-01`
的「全 0」（上面那条），一次是 `LITERACY-26` 的「流水恰好一条」——
后者不是本轮写错的，是本轮的功能把一条既有断言撞翻了：那份「2000 字全学过」的存档
顺带满足 `char-50`，挂上结算后同一次调用多出一条解锁流水。
**这次失败是有用的**，它是「四条打卡路径都接上了」的直接证据。改断言，不改功能。

**「先 format 再 check」第四次生效，仍然一次全绿。** 已固化在 tasks.md 收尾节。

**跨域规格被本域进展打翻，第二次。** 上一轮是 `LEARN-02`（点亮灰格子），
这一轮是 `LITERACY-26`（挂上结算）。两次的形状一样：**A 域的不变式建立在
「B 域还没做」这个隐含前提上**，而那个前提没写在断言旁边。这次的注释写明了
「P3-b 起 checkAwardAndGrow 末尾会结算奖励」，下一个人读到那行就知道为什么只数一条。
`STICKER` 与 P7 大概还会各演一遍。

**存储层先行第三次省掉了返工。** `lastWeeklyBonusWeek` 与 `redemptions` / `achievements`
的元素收敛在写 `reward.js` 之前就落好了（`SAVE-14` ~ `16`、`IMPORT-12` / `13`），
所以 `reward.js` 里一处 `?? 0` 都不用为脏存档写 —— 读取入口只需要保证「是个数组」。
